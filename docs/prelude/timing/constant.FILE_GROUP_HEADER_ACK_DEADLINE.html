Expand description

The deadline, 15 s, for the receiver to answer one file-transfer group’s header. Past it the sender fails the transfer with ErrorCode::FileTransferStalled. The clock runs only while no earlier group of the session is still in flight: every header and payload of a session shares one primary stream, so a header queued behind another group’s payload is not the receiver’s to answer until that payload has drained.

What it is sized against. The header travels on a channel that is already established, and the receiver answers it as soon as it reads it, so the wait is one round trip on that channel. The worst round trip assumed is that of a relayed link across the internet. The protocol keeps no measured round-trip time or per-packet ack timeout to size this against (its keep-alive timeout is 45 minutes, sized for idle sessions, not for answers), so the yardstick is TURN_CONNECT_TIMEOUT (10 s): the time this protocol already allows a TURN connect across the internet, which is two and a half handshake round trips over the same kind of path. One round trip on an established relayed channel therefore fits well inside 10 s; the deadline is half again as long, for a loaded relay.

The latest the failure is reported is this deadline plus one FILE_GROUP_CHECK_PERIOD (1 s): FILE_GROUP_HEADER_UNANSWERED_FAILS_WITHIN, 16 s.

How long a header can stay queued. It waits only while an earlier group of the session is in flight, and each of those is bounded in turn: it completes, or its own unanswered header fails within 16 s once first in line, or, answered, it is failed once its acks stop for GROUP_EXPIRE_TIME_MS (60 s) on a silent session or ten times that (600 s) on a busy one. The earlier groups run those clocks at the same time, not one after another, so a header queued behind groups that have all stalled is failed at most about 600 s + 16 s after it was sent. Behind groups that keep moving it waits as long as they move: that is a queue, not a stall.
